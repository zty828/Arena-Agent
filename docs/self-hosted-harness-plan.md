# Harness 前端：方案与范围

日期：2026-09-17（同日两次修订，本文为最终版）。

> **先读这一段（2026-09-19 更新）。** 本文是**方案文档**，写于前端还不存在的时候；文中「现状」「要做什么」的时态请按历史记录读。**该前端已经实现**：`apps/desktop/` 的 Electron 窗口就是它——三栏布局（工作区与目录树 / 待办·活动·文件·授权·事件 / 上下文检查器）、窗口内一键隧道、补丁审批、无人值守写入开关，入口是 `desktop.cmd`，自检 53 项在 `npm run verify` 里。文中关于**边界**的结论（前端不持有权限、只做本机、不做的事）依然有效，是当前实现遵循的约束。

**上一版方案已被否决，此处记录原因以免重复犯错。** 上一版假设需要"自选模型 provider（DeepSeek/Kimi/Ollama）+ 在 harness 内跑 agent 循环"，并围绕它设计了 `provider_gateway_bridge_tools` 模式。用户明确纠正：

> 让 Arena 模型在本机环境下去操作，而不是再额外接入其他 API。之前不是已经实现了让 ArenaAI 使用工具读写本地文件了吗，现在要做的只是完善这套流程并且加上一个 Harness 前端。

所以：

- **模型永远是 Arena 的。** 不接第二个 provider，不新增推理后端，不在本机跑模型循环。
- **已完成的部分是基础，不是原型。** 远端模型已经能通过 MCP 调用本机工具读写文件（`apply_patch` 全链路今天实测跑通）。这条链路是要保留并加固的主体。
- **要补的是"前端"**：一个让人看得见、管得住、能介入的本机界面。

---

## 1. 现状：链路已经通了，只是没有脸

今天实测通过的完整写路径（`scripts/write-cycle-e2e.mjs`，22/22）：

```
pair(code) → 本机批准 → claim → challenge → tools
  → apply_patch(preview)   真实 diff + patch_id，磁盘未变
  → 控制台读 diff          操作者审阅
  → 本机批准               approval_id
  → apply_patch(apply)     磁盘真的改了
  → 重放                   不重复执行，approval 已消费
```

审计侧独立可核：`grant.issued` → `grant.verified` → `tool.completed` → `approval.requested` → `approval.decided` → `approval.consumed`，无 `tool.failed`，事件里无凭据、无文件正文。

**能力是有的。缺的是操作者视角。**

## 2. 为什么需要一个"前端"

现在操作者要批准一个补丁，必须：

1. 知道去看 `http://127.0.0.1:48272`（端口还得从 `daemon.ready` 里抄）；
2. 用 `admin_token` 解锁（而配对码长得一模一样，今天就栽在这上面）；
3. 在 `/admin/v1/status` 的 JSON 里找一个 `approvals[].id`；
4. 用 `curl` 或某个页面 POST 一个 decision。

这四步里任何一步错，远端 agent 就卡在 `waiting_for_approval` 等到超时（默认 120s）。**当前控制台的定位是"取证面板"，不是"操作台"。**

### 三个具体痛点

| 痛点 | 后果 |
|---|---|
| 待审批项不显眼、不主动提示 | 远端干等到 `approval` 过期 |
| diff 要自己从 JSON 里读 | 审阅质量差，容易盲批 |
| 没有"这个 run 正在干什么"的实时视图 | 出问题时只能翻 `event_log` |

## 3. Harness 前端要做什么

一个本机单页操作台，**不引入新后端、不引入模型、不改变安全模型**。

### 3.1 三块核心视图

**① 待办中心（最重要）**

- 待审批卡片的实时列表：谁（recipient）、要改哪个文件、diff 是什么、什么时候过期。
- diff 用并排视图渲染（`+`/`-` 着色），不是 JSON 字符串。
- 允许 / 拒绝一键操作，带倒计时。
- 浏览器通知 + 声音：有新的写请求时主动提醒，不靠人盯。

**② Run 时间线**

- 按 `run_id` 分组，把 `event_log` 渲染成人话：
  `已授权 → 读了 3 个文件 → 请求修改 sum.mjs → 已批准 → 已应用`
- 每个工具调用显示 `params_hash`、`duration_ms`、`execution_owner`。
- 失败的调用单独标红，附错误码（这正需要今天修好的错误码透传）。

**③ 授权台账**

- 当前活跃 grant：模式（ask/plan/code）、到期时间、剩余额度。
- 一键 `revoke_all`（已有 `policy.revokeAll()`）。
- 明确显示"此刻远端能做什么"——这是所有人最关心的问题。

### 3.2 一个关键设计决定：前端不持有权限

前端**只调用已有的 admin API**，不新增任何旁路：

- 它不持有 `admin_token`——沿用已有的 `#t=<token>` URL fragment 自动解锁（已实现），解锁后 token 存在 `sessionStorage`，刷新即失效。
- 审批走现有 `POST /admin/v1/approvals/:id/decision`。
- 撤权走现有 `POST /admin/v1/revoke`。
- 读事件走现有 `GET /admin/v1/events`。

**没有任何新权限面。** 前端拿不到的东西，后端也拿不到。

### 3.3 只做本机

监听在已有的 `ports.admin`（默认 48272），只 loopback。不开新端口，不碰 tunnel 端口。

## 4. 实现形态

现有 `apps/daemon/src/console.ts` 是一个单文件、无构建步骤的 HTML（inline CSS/JS）。**继续沿用这个形态**：

- 不引入 React/Vite/打包链——这套东西的价值是"打开就能用"，多一个 `npm run dev` 就少一半可靠性。
- 页面直接用 `fetch` + `EventSource`（SSE）订阅 `GET /admin/v1/events` 做实时推送。
- 现有 console 页面升级，而不是新建一个并行入口（否则又变成"两个地方要看"）。

预计规模：`console.ts` 从当前约 1 个简单页扩到约 3 个 tab，仍然是单文件。

## 5. 依赖关系（必须先做完的）

今天已完成的，是 Harness 前端的前提：

- [x] 写路径全链路可用（preview → 审批 → apply）
- [x] 错误码正确透传（`APPROVAL_REQUIRED` 不再被压成 `PATCH_APPLY_FAILED`）
- [x] 审批被拒后补丁可重试（不再被烧成 `rolled_back` 死态）
- [x] 全量回归 87/87

前端可以直接建在这之上。

## 6. 边界：前端不做的事

明确写出，避免范围蔓延：

| 不做 | 原因 |
|---|---|
| 不在前端跑模型循环 | 模型是 Arena 的，这是用户明确要求 |
| 不接第二个 provider | 同上 |
| 不新增权限 | 前端只消费已有 admin API |
| 不做多用户 / 登录系统 | 本机单人工具，`admin_token` 就是身份 |
| 不做历史归档 / 报表 | 需要的是实时操作台，不是 BI |

## 7. 一个必须说清的点

前端让**本机操作者**更舒服，但它**不改变**远端能做什么——远端仍然只能做 grant 允许的事，仍然每个写操作都要人批。这是特性，不是缺陷。

真正的风险点在别处且仍未解决：**Arena 侧的评测数据是公开的**（官方原文：任务描述与结果摘要会进公开 agent 排行榜）。前端管不了这个，只能在文档里持续提醒：**任务描述里不要放敏感信息。**

## 8. 建议的施工顺序

1. **待办中心**（解决最容易出事的一环：审批过期）
2. **Run 时间线**（解决"它在干什么"）
3. **授权台账 + 一键撤权**（解决"它现在能做什么"）

第 1 步做完就应该能显著减少"远端干等超时"这类问题。第 2、3 步是运维舒适度。
